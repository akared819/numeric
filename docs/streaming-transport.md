# Acknowledged streaming protocol

`numericAcknowledgedStats` is a single-producer, one-event-at-a-time aSub interface. It uses one DOUBLE waveform for the entire event so sample and identity are fetched together. It is not a general-purpose queue: reliable delivery within a running session requires the producer to follow the acknowledgment protocol below. Independently writing or overwriting the event waveform without waiting for acknowledgment can lose events.

Call `numericInitialize` after registering the IOC support and before `iocInit`. Use [acknowledged-stats.db](../examples/acknowledged-stats.db): the passive, synchronous soft waveform must have a **local database forward link** to the passive aSub record, and the aSub must read that waveform through a **local database input link**. Do not force either link through Channel Access. Do not disable, periodically scan, or separately process either record. The waveform VAL field processes the waveform on a CA put; its forward link then processes the aSub under the same database lock set. The sender requires this configuration and cannot verify it remotely. Configure input A as DOUBLE with `NOA` at least 5; each valid input must contain exactly four DOUBLE values `[session, sequence, kind, value]`. A fifth element is rejected, including when the input is truncated at capacity. Use a scalar-output DOUBLE `aSub` record with `SNAM=numericAcknowledgedStats`. Its first seven outputs, VALA–VALG, are mean, sample variance, sample standard deviation, RMS, minimum, maximum and count. VALH is the acknowledged session, VALI the sequence, VALJ the event kind and VALK the event value. All eleven outputs must be scalar DOUBLE fields. The example forwards these two acknowledgment fields to separate PVs. Variance and standard deviation are NaN after the first sample. Reset yields NaN for statistics and zero count.

The session is an integer in `[1, 2^53]`, chosen uniquely by the producer for each new stream lifetime. The first sequence is zero; subsequent sequences increase by exactly one up to `2^53`. Kind 0 is a sample, and `value` must be finite. Kind 1 is a reset, and `value` must be zero. A reset is an ordered event and consumes a sequence number. When the IOC, record, or subroutine is restarted or replaced, its state is lost: the producer must choose a new session identifier and begin at sequence zero. Session reuse across restarts cannot provide exactly-once behavior.

For each event, a single coordinated producer must:

1. Write the complete waveform using a Channel Access put callback and wait for completion. The local forward link processes the aSub before the callback completes; do not issue a separate `.PROC` write.
2. Check record `VAL` is zero and read the acknowledgment. Accept it only when session, sequence, kind and value all match the submitted event. The seven statistics accompany that acknowledgment. Channel Access put completion alone is not the numerical acknowledgment.
3. Do not submit the next event until acknowledgment. On a lost or ambiguous response, retry the identical event. The consumer replays the retained acknowledgment without updating state twice. A late old waveform write is processed together with that write while the lock set is held: it is rejected if a later event has already been accepted, and cannot overwrite an unprocessed newer event. A repeated sequence with a different kind or value, a sequence gap, a lower sequence, a different session, an invalid sample or malformed packet is rejected with CALC/INVALID.

An old delayed request can still change the record's status after a newer event is processed. Therefore a nonzero `VAL` or mismatched acknowledgment is **uncertain**, not proof that the current event was rejected. Retain the current event and investigate or retry it; never advance solely on a put callback. Separate acknowledgments and statistics are not an atomic read, so independent processing or writers are prohibited.

This is cooperative backpressure: the IOC does not reserve the waveform slot or enforce exclusivity against another client. It does not persist samples or acknowledgments over an IOC crash, detect overwritten events before its first processing, or guarantee delivery if a producer violates the protocol. Multiple independent writers require an external arbiter. Session and sequence output links are separate EPICS operations, not an atomic pair; read them only after the matching process completion while holding the single-producer discipline. If a numerical failure poisons the workspace, an ordered reset can be sent using the still-expected sequence; the failed sample is not acknowledged. A reset allocates a new workspace before replacing the old one, and a failed allocation leaves the prior acknowledgment intact. GSL's documented upstream allocation-failure caveat still applies.

## Native Channel Access sender

The build provides `numericAckSend`, a native command-line producer for a single event. With the example database loaded using prefix `demo:`, run these commands in order:

```sh
numericAckSend demo:event demo:acknowledgedStats 57 0 sample 1.5
numericAckSend demo:event demo:acknowledgedStats 57 1 sample 2.5
numericAckSend demo:event demo:acknowledgedStats 57 2 reset
```

Both the waveform forward link and the aSub input must be local database links as in the example; the passive waveform and aSub must process synchronously. Configure Channel Access addressing for the IOC as usual. The sender waits for waveform put completion (including the forward-linked processing), verifies record `VAL` and all four acknowledged event fields, then prints the seven statistics in the order above. It attempts the identical event up to three times, with a five-second timeout for each connection, put, or read step. Exit status 0 confirms acknowledgment; 1 reports invalid input; 2 means the outcome is uncertain, including a nonzero IOC status. After an uncertain outcome, retain and retry the **identical** event before sending a later sequence. A nonzero IOC status can indicate a sequence or input error or interference from a delayed request; inspect the IOC state when retries cannot resolve it.

The executable does not choose or persist session numbers, queue events, arbitrate multiple producers, or recover IOC state after restart. The caller must ensure only one event is in flight and maintain its event and sequence across process invocations. Retrying does not make an uncoordinated producer lossless.

The native `numeric::AcknowledgedStream` API in `numericAck.h` implements the same sequencing and caches the last response. `create()` requires GSL initialization and can return null; allocation exceptions can propagate. `submit()` reports errors without replacing the caller's acknowledgment, and sets `replayed` on identical retries. Callers must serialize access to each instance. Each instance owns its GSL workspace and releases it on destruction. The IOC adapter stores one instance per record, releases it when the aSub routine changes or at process exit, and does not support dynamic database deletion/recreation within a process.

The native and IOC suites test sequencing, duplicate identity, invalid inputs, reset, independent instances, and oversized packets. `numericAckCaTest` uses a local CA client to submit events, destroy and recreate its channels, retry an event and issue a reset; it also exercises the sender's acknowledgment, duplicate, rejection, reset, validation, unavailable-IOC, and a delayed older write delivered after a newer acknowledgment. The test injects ordering at the application level; it does not simulate an actual network partition, a lost response after processing, IOC crash, arbitrary concurrent writers or durable recovery. See [EPICS process notification](https://docs.epics-controls.org/en/latest/appdevguide/lockScanProcess.html) and [CA put callback semantics](https://docs.epics-controls.org/projects/base/en/7.0.10/cadef_h.html).
