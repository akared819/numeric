# numericArray record

`numericArray` is a synchronous EPICS record for compatible stateless registry operations that produce one DOUBLE array. Input links must be nonconstant and report DOUBLE type. Configure OP at database load time; it cannot be changed at runtime. The supported operations include:

| OP | Input and output | Parameters |
| --- | --- | --- |
| `moving_mean`, `moving_median` | Real array to same-length real array | WIN: odd window length |
| `gaussian_smooth` | Real array to same-length real array | WIN and ALPH: window length and Gaussian alpha |
| `fft_complex_radix2_forward`, `fft_complex_radix2_inverse` | Interleaved complex input to equal-length interleaved complex output | None |
| `fft_real_radix2_forward` | Real input to full interleaved complex spectrum | None |
| `histogram_uniform` | Real samples to uniform bin counts | HMIN, HMAX and NBIN: lower/upper range and bin count |
| `linear_fit` | Two real arrays to six fit outputs | None |

For one numerical input configure INP or INPA; for multiple inputs configure contiguous INPA, INPB and subsequent links in registry input order, excluding configuration arguments. Specifying INP and any INPA–INPP link together, omitting a required link or specifying a surplus link fails initialization. See [multi-input.db](../examples/multi-input.db) for a two-waveform `linear_fit` example. Separate links are read in order and do not provide an atomic cross-PV snapshot; coordinate input updates before processing.

WIN, ALPH, HMIN, HMAX and NBIN are writable DOUBLE fields; changing them does not itself process the record. Their bounds, endpoint convention, FFT lengths, output representation and numerical behavior are specified in [window statistics](window-statistics.md), [FFT](fft.md) and [histograms](histograms.md). The operation is evaluated against the current fields at processing time; a producer changing input and parameters must coordinate them. Other registry operations are rejected at initialization rather than being mapped to incompatible fields.

`ARGA` through `ARGP` are writable string fields. A nonempty field overrides the corresponding legacy parameter on the next process: window operations use ARGA for WIN and Gaussian smoothing uses ARGB for ALPH; histograms use ARGA, ARGB and ARGC for HMIN, HMAX and NBIN. A blank override restores the legacy field. FFTs take no arguments. An unused nonempty ARG field causes CALC/INVALID on processing. Writing a field does not itself process the record.

Enter integers in decimal, with no whitespace; floating values use a decimal point and may use scientific notation. Text must be at most 38 characters: a 39-character field is rejected because EPICS may have truncated a longer write. Integer text is parsed as a signed 64-bit value and is rejected if it cannot be represented exactly by the existing double-based execution interface. Invalid arguments retain the previous VAL and NORD. All fields are read while the record is locked for processing, but separate writes from a client are not a transaction; coordinate writes and processing if several values must change together. Parsing a changed nonempty ARG field may allocate memory; each record caches successfully parsed values for unchanged fields.

For example, `caput demo:arrayMean.ARGA 5` followed by `caput demo:arrayMean.PROC 1` selects a five-sample window; write an empty string to ARGA to use WIN again.

NMAX is the maximum waveform input count and OMAX the output capacity, each 1 through 1,048,576 doubles and fixed at database load. An extra element per waveform input detects truncation: an input longer than NMAX is rejected, while an exact NMAX-element input is accepted. Scalar inputs use a two-element buffer to detect excess elements. OMAX must accommodate the complete result, including 2N elements for an N-sample real FFT. VAL is a read-only DOUBLE array. On success NIN is the number of elements used from the first numerical input and NORD is the number of output doubles; on failure NIN becomes zero while VAL and NORD retain the last successful result. Check SEVR and STAT when consuming the value.

Call `numericInitialize` before `iocInit`, after registering support. Processing fetches the input links, validates inputs and parameters, performs the operation, and copies the complete staged result to VAL only on success. Success clears UDF and posts value/log monitors; the timestamp is refreshed on every processing attempt. Errors raise CALC/INVALID and post alarm changes without replacing the last result. The forward link runs after every attempt, including failures. Input updates do not automatically process the record. There is no output link: clients may monitor VAL or other records may use it as an input link. EPICS link acquisition and client delivery have their normal asynchronous semantics and are not acknowledged by this record.

Each record owns a buffer for each input, two OMAX-double buffers for staging and published output, and its own operation instance. The real FFT, window and histogram operations may additionally allocate reusable scratch or GSL workspace on first use or size changes during processing; see their operation guides. Resources are registered with `epicsAtExit` and are freed when the IOC calls `epicsExit` or `epicsExitCallAtExits`. Returning from `main` or termination by a signal does not itself run these EPICS callbacks, although the OS reclaims process memory. Dynamic database deletion/recreation in a running process is unsupported; per-record resources are not freed at IOC shutdown before process exit. No record shares a mutable computational workspace. Initialization failure, invalid configuration or allocation failure leaves the record unavailable; subsequent processing raises an invalid alarm.

Include `numericSupport.dbd`, `numericScalarRecord.dbd` if used, and `numericArrayRecord.dbd` in the IOC application DBD and link `numericIoc` and `numeric`. [array.db](../examples/array.db) demonstrates moving statistics, Gaussian smoothing, a real FFT and a complex inverse. The standalone example loads it with prefix `demo:`. For example, write `demo:arrayInput`, process `demo:arrayMean`, then read `demo:arrayMean.VAL` and `demo:arrayMean.SEVR`.
