# Phase 4: dedicated record support plan

The completed general-purpose scope and evidence are recorded in [Phase 4 acceptance](phase4-acceptance.md). Phase 4 introduces a small pair of native EPICS record types using the existing operation registry, without creating a record per GSL routine. The target is the general-purpose module and bundled example IOC on the supported EPICS Base 7 Linux configuration. The [Phase 3 acceptance boundaries](phase3-acceptance.md), including the unresolved Base notification crash and GSL error-handler policy, continue to apply.

1. `numericScalar` reads one DOUBLE scalar or waveform input and produces a scalar result using a compatible stateless array-to-scalar registry operation. Validate the operation descriptor, count and type; report errors and preserve the last result. Provide IOC and separate-client tests and an example.
2. `numericArray` reads and produces DOUBLE waveforms using a small explicitly supported subset of array-to-array operations. Specify operation parameters, input and output capacities, per-record workspace ownership and output publication before implementation; cover FFT and window operation cases as practical.
3. Integrate both records in the standalone IOC, test numerical results, invalid and truncated inputs, alarm/recovery, timestamps, value and alarm monitors, forward links, and process lifetime. Run native, IOC and separate-process CA tests with the existing Linux suite.
4. Record the actual tested scope, limitations, setup and acceptance evidence. Review and merge each small PR after required checks pass; Phase 4 closes only when the record types and general-purpose example meet these criteria.

Common constraints: initialize GSL once before concurrent use; use per-record resources with cleanup through EPICS exit callbacks; do not expose GSL pointers as public fields; do not silently truncate; treat record processing as synchronous and do not assume input updates cause processing. Define handling of links, field access, allocation failures, alarm state and operation changes explicitly. No Python runtime or new numerical dependency is required. Dynamic database removal/recreation and asynchronous solver support require explicit investigation before being claimed.

Record support is implemented using EPICS Base's documented record-support entry table and database link and event APIs. Consult the [EPICS record support documentation](https://docs.epics-controls.org/en/latest/appdevguide/recordSupport.html), [common fields](https://docs.epics-controls.org/projects/base/en/latest/dbCommonRecord.html), and [waveform record](https://docs.epics-controls.org/projects/base/en/latest/waveformRecord.html); validate behavior against the supported Base release rather than relying on assumptions about arrays or record lifetime.
