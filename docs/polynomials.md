# Polynomial evaluation

`polynomial_eval` evaluates a real polynomial using GSL's [`gsl_poly_eval`](https://www.gnu.org/software/gsl/doc/html/poly.html#polynomial-evaluation). It takes a nonempty contiguous DOUBLE coefficient array followed by one finite DOUBLE scalar evaluation point and returns one DOUBLE scalar. Coefficients are ordered by ascending power: `[c0,c1,c2]` represents `c0 + c1*x + c2*x²`. For example, `[2,3,4]` at `x=2` returns 24. A single coefficient represents a constant polynomial.

The coefficient count must fit in `int`, the type used by GSL's API; stride must be one and capacity must cover all coefficients. The point must have scalar shape, exactly one valid element, capacity of at least one, and unit stride. All input values must be finite. Empty or invalid buffers, NaN and infinities return `InvalidArgument`. A non-finite calculated result returns `NumericalError`; this can occur when floating-point intermediate results overflow even if an exact mathematical expression exists. Failure clears the output count and preserves the previous output value. Ordinary floating-point rounding and underflow are not separately diagnosed. The caller owns input and output buffers. The operation is stateless, has no workspace and allocates no memory during execution; initialize the GSL policy as described in [architecture](architecture.md#gsl-setup-for-an-ioc).

`numericPolynomial` exposes the operation via an aSub record. Configure A as a nonconstant link to a DOUBLE coefficient waveform, with NOA strictly greater than its maximum valid length to detect possible truncation. Configure B as one DOUBLE scalar (a constant or a link that reports DOUBLE type), and VALA as one DOUBLE output. A configured OUTA must report DOUBLE type and scalar capacity; a disconnected or incompatible link is rejected. EPICS may fetch and convert linked values before the routine is called, but the routine rejects non-DOUBLE source and target links rather than accepting that conversion. The record fetches A and B separately, so a producer must coordinate them if they must represent the same update. Input changes do not automatically schedule record processing. On invalid input, missing initialization or numerical failure the routine clears NEVA, raises CALC/INVALID and returns -1; the previous downstream output is retained. See [polynomial.db](../examples/polynomial.db) for a runnable example; the standalone IOC loads it under the `demo:` prefix. For example, write `[2,3,4]` to `demo:polyCoefficients`, set `demo:polyPoint` to 2, process `demo:polyEval`, and read `demo:polyResult` and the record alarm.
