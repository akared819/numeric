# Moving mean, median and Gaussian smoothing

`moving_mean`, `moving_median` and `gaussian_smooth` are batch operations over a finite, nonempty FLOAT64 array with at most `INT_MAX` elements. Their first input is the signal (contiguous stride 1), and the second is a FLOAT64 scalar window length K. K must be an odd integer from 3 to 4095 and cannot exceed the signal length. The Gaussian operation takes a third FLOAT64 scalar, `alpha`, restricted to 0.01 through 10 inclusive. These conservative limits are part of numeric's interface, not a claim about all values supported by GSL. Output is one FLOAT64 array with the same element count as the input.

The window is centered, with `(K-1)/2` samples on either side. At the boundaries, the first or last value is repeated to fill the window (GSL's PADVALUE). The moving mean returns the arithmetic mean of each window. The moving median returns the middle value of each odd-length window, using GSL’s `gsl_movstat_median`; an isolated spike surrounded by equal values is removed. Gaussian smoothing uses GSL's normalized zeroth-order Gaussian kernel, with `sigma = (K-1)/(2*alpha)` in sample units. It does not perform differentiation, causal streaming, resampling or missing-data interpolation. For example, K=3 moving mean of `[1,2,3,4,5]` is `[4/3,2,3,4,14/3]`; alpha `sqrt(2*ln(2))` produces weights `[1/4,1/2,1/4]` for K=3. See the official [GSL moving statistics](https://www.gnu.org/software/gsl/doc/html/movstat.html) and [filter documentation](https://www.gnu.org/software/gsl/doc/html/filter.html).

A registry instance owns its GSL workspace. The first execution and any change in K allocate a replacement workspace; subsequent calls with the same K reuse it. `reset()` and destruction release it. Independent instances own independent workspaces; do not call one instance concurrently. Workspaces contain scratch, not a history of previous signals. Allocation failures are reported when GSL returns a failure; as with other GSL users, the process-wide non-aborting handler must be initialized before execution. The separate running-statistics allocation caveat is described in [streaming](streaming.md).

Input and output buffers may be identical or disjoint; partial overlap is rejected. Types, counts, capacities, stride, finite values and parameters are validated before a calculation. On invalid input the data are unchanged and output count is zero. On a GSL or numerical failure, output count is zero but output contents are unspecified, including the input for in-place execution. A caller needing preservation on numerical failure must use separate buffers. Non-finite results are rejected; underflow and roundoff are not separately diagnosed. The caller owns all buffers and must keep them valid and unmodified by other threads during execution.

## EPICS aSub interface

`numericMovingMean`, `numericMovingMedian` and `numericGaussianSmooth` read the signal from A, window length from scalar B, and for Gaussian smoothing alpha from scalar C. Configure all used fields and VALA as DOUBLE, B and C with exactly one element, a nonconstant INPA, NOA greater than the maximum source length, and NOVA at least the source length. A full input buffer is rejected because it could have been truncated. Output links, if configured, must report DOUBLE type and sufficient capacity; disconnected or indeterminate links fail validation. EPICS link delivery can still fail after validation and is not acknowledged.

Each record creates and owns its own operation and workspace, releasing them when the record support invokes its cleanup callback. Workspace creation and changes in K allocate during record processing; stable K reuses the workspace. Numerical work uses the record's A buffer as scratch, so A no longer contains the original input after processing. VALA and downstream output are updated only after success. On a calculation or validation failure, the routine clears NEVA, sets CALC/INVALID and returns -1; aSub does not push output links. A failed input fetch follows EPICS record support semantics and can occur before the routine runs. Check record and link status. Updating an input link does not itself schedule processing.

[window.db](../examples/window.db) supplies a five-sample example with K=3. After loading it and calling `numericInitialize` before `iocInit`, write `windowInput`, then explicitly process `movingMean`, `movingMedian` or `gaussianSmooth`. The example uses separate output waveforms. Scalar parameters may be updated between calculations; producers must coordinate signal and parameter updates if a consistent set is required. See [EPICS aSub](https://docs.epics-controls.org/projects/base/en/latest/aSubRecord.html).
