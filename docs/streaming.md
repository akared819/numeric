# Running mean core operation

`running_mean` consumes exactly one finite Float64 scalar sample per `execute` and returns two Float64 scalar outputs: the running mean and accepted sample count. Each successful call counts one sample; invalid inputs are rejected without changing state. A caller must not interpret repeated execution as a new sample unless its own triggering protocol guarantees that.

The first accepted sample produces that value and count 1. There is no zero-sample output: `reset()` clears the workspace and the next successful execution again returns count 1. Counts are exact up to 2^53, or the platform's smaller `size_t` limit; updates beyond that limit are rejected. Input/output descriptors require a scalar, count and capacity at least one, unit input stride, distinct output buffers and Float64 types. On failure both output counts are cleared and output values remain unchanged. Non-finite inputs are invalid. GSL update errors or non-finite means invalidate the accumulator until reset, since the update may already have changed its internal state. Reset failures leave the instance invalid. No variance convention is defined by this operation.

Call `initializeGsl()` during single-threaded process startup before creating a running operation: its factory allocates the GSL workspace and returns null if GSL is not initialized or allocation fails. Each successfully allocated instance owns its `gsl_rstat_workspace` and frees it on destruction; no allocations are made per update. Allocation-failure caveat: inspection of the locally built GSL 2.8 source shows `gsl_rstat_alloc()` can leak its outer allocation if its internal median-workspace allocation fails. The public API returns null without exposing that allocation, so numeric cannot reclaim it; this rare upstream failure path has not been fault-injection tested. Do not use a single instance concurrently without synchronization. Independent instances have independent sample counts and resets. These guarantees depend on all process participants honoring the global GSL error-handler policy in [architecture](architecture.md). See [GSL running statistics](https://www.gnu.org/software/gsl/doc/html/rstat.html).

## EPICS aSub prototype

See [running-mean.db](../examples/running-mean.db). Configure `SNAM` as `numericRunningMean`; inputs A, B and C and outputs VALA and VALB are DOUBLE scalars with capacity 1. Input links must be constants or report exactly one source element; links to larger waveforms or links that cannot report their size are rejected to avoid silent truncation. A is the sample, B is its sequence number, C is the reset token, VALA is the mean and VALB the count. Sequence and reset tokens must be exactly representable nonnegative integers no greater than 2^53. Every record owns an independent workspace.

The first processing accepts the sample and establishes the initial reset token. Thereafter each accepted sample requires a strictly increasing sequence number. Reprocessing the same sequence returns VAL=1, clears NEVA/NEVB, and does not update state or output links. A lower sequence is rejected with CALC/INVALID. Invalid samples or tokens return VAL=-1, set CALC/INVALID, clear output counts and do not consume the sequence; a numerical failure may require reset as described above. Consumers must check VAL and alarm state.

Increase the reset token and process the record to clear state. This processing consumes no sample and outputs count zero and a NaN mean (there is no mean for zero samples). The sequence number is not reset: the next sample must have a sequence greater than the last accepted one. A decreasing reset token is rejected. Counters do not wrap; restart the IOC to start a new sequence after reaching the limit. An IOC restart clears all state.

The IOC integrator must deliver sample, sequence and reset coherently: aSub fetches the three links separately, not as an atomic transaction. The example is for a single coordinated producer: write the sample, write the next sequence, then process `$(P)runningMean.PROC`; do not concurrently modify them during processing. Similarly, change the reset token and process it separately before sending a new sample. Input links do not automatically process the record, and passive records can miss intermediate updates. This prototype does not provide a queue or guarantee one calculation per external PV update. It is not suitable for independent or unsynchronized producers or network delivery requiring lossless event association.

State is created on first processing after `numericInitialize`, retained per record and released when aSub changes its subroutine or at process exit. EPICS serializes processing of an individual record; workspace operations are not shared between records. This prototype does not support dynamically deleting and recreating databases in one process; use normal IOC process lifetime. The GSL allocation-failure caveat above remains.

## Grouped running statistics

The `running_stats` core operation and `numericRunningStats` aSub routine maintain one independent GSL `gsl_rstat` workspace per instance. Each accepted sample returns seven DOUBLE scalar outputs in order: mean, sample variance, sample standard deviation, RMS, minimum, maximum, and count. Variance uses the `N-1` denominator; standard deviation is its square root. RMS uses the square root of the average squared samples. After the first sample the variance and standard deviation are undefined and are returned as NaN; mean, RMS, minimum and maximum are defined. Reset outputs NaN for all six statistics and zero for count. The first sample after reset starts a new count at one. A non-finite computed statistic invalidates the workspace until reset. Inputs, output capacity and non-finite samples are validated before state changes; output buffers must be distinct. Allocation and shutdown follow the running-mean policy and caveat above.

Configure inputs A, B and C as in `numericRunningMean`; configure VALA through VALG as DOUBLE scalar outputs for the seven values above. See [running-stats.db](../examples/running-stats.db). For this new routine, after the first accepted sequence each new sequence must equal the previous sequence plus one. Repeated sequences are ignored with VAL=1; gaps or decreases signal CALC/INVALID without consuming a sample. A failed sample can be retried with the same expected sequence. A reset token increment consumes no sample and retains the last sequence; the next sample must have the next consecutive sequence. Counts and tokens are exact only up to 2^53. As with running mean, input links are read separately and do not schedule processing. The producer must update the sample and sequence coherently and process the record once per event. Gap detection reports some missed events but cannot recover them or detect a mismatched sample and sequence; it is not a lossless queue. For a coordinated single producer, see the [acknowledged streaming protocol](streaming-transport.md).
